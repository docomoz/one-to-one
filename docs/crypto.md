# Шифрование пары

Как телефон шифрует записи пары, прячет их id и передаёт ключ пары на другое устройство.
Описание точное до байта, чтобы Android и веб повторили его и читали те же данные.
Код: `Packages/OneToOneKit/Sources/Sync/Crypto/`, тесты: `Packages/OneToOneKit/Tests/SyncTests/CryptoTests.swift`.
Тест `testVectorsMatchDocs` читает векторы прямо из этого файла: поменяли формат — поменяйте векторы, иначе тест упадёт.

## Алгоритмы

Только стандартные, есть на всех платформах:

| Что | Алгоритм | Стандарт |
|---|---|---|
| Шифрование записей и ключа | AES-256-GCM, nonce 12 байт, тег 16 байт | NIST SP 800-38D |
| Обмен ключами | X25519 | RFC 7748 |
| Вывод ключей | HKDF-SHA256 | RFC 5869 |
| Id документа | HMAC-SHA256 | RFC 2104 |
| Проверочный код | SHA-256 | FIPS 180-4 |

Обозначения: `||` — склейка байтов, `utf8(s)` — байты строки в UTF-8 без завершающего нуля,
`hex` — строчные шестнадцатеричные цифры, по две на байт.

## Ключ пары

32 случайных байта из системного генератора (`CoupleKey`). Создаётся один раз при создании пары, хранится только
в Keychain устройств партнёров. На сервер попадает только завёрнутым для конкретного устройства (см. «Обмен ключами»).
Новая пара всегда получает новый ключ.

## Конверт записи

Каждая запись шифруется ключом пары напрямую (`RecordCipher`):

```
nonce    = 12 случайных байт, новые для каждого шифрования
aad      = utf8(coupleID || "/" || documentID)
ct, tag  = AES-256-GCM(ключ пары, nonce, открытый текст, aad)
конверт  = 0x01 || nonce (12) || ct (как открытый текст) || tag (16)
```

- `coupleID` — id команды Appwrite этой пары, `documentID` — 32 hex-символа из следующего раздела.
- AAD привязывает конверт к документу и паре: сервер не может переложить конверт в другой документ или другую пару.
  Разделитель `/` однозначен, потому что в id Appwrite нет `/`, а `documentID` всегда 32 hex-символа.
- Первый байт — версия формата. Сейчас только `0x01`. Конверт другой версии не открывается (`unsupportedVersion`),
  а не читается как мусор.
- Длина конверта = длина открытого текста + 29. Меньше 29 байт — испорчен (`invalidEnvelope`).
- На сервере конверт лежит в base64 (стандартный алфавит, с `=`), см. коллекцию `records` в плане.

## Id документа

Сервер не должен по id понять вид и дату записи (`"period:2026-10-11"`). Поэтому id документа — HMAC от id записи
(`RecordIDHasher`):

```
ключ_id      = HKDF-SHA256(IKM = ключ пары, salt = пусто, info = utf8("one-to-one record-id v1"), L = 32)
documentID   = hex(первые 16 байт HMAC-SHA256(ключ_id, utf8(recordID)))   // 32 символа
```

- Пустая соль по RFC 5869 равносильна 32 нулевым байтам: HMAC дополняет короткий ключ нулями.
- Один `recordID` в одной паре всегда даёт один `documentID`, у другой пары — другой.
- Отдельный `ключ_id`, а не ключ пары: один ключ — один алгоритм.

## Обмен ключами

Так ключ пары попадает на телефон партнёра (приглашение) и на новый телефон (восстановление).
Сервер передаёт только открытые ключи и завёрнутый ключ.

1. Каждое устройство создаёт для этого обмена новую пару X25519 (`KeyExchangePair`) и кладёт на сервер открытый ключ
   (32 байта, base64).
2. Оба устройства показывают проверочный код из двух открытых ключей. Партнёры сверяют его голосом или в переписке.
3. Только после подтверждения устройство с ключом пары заворачивает его для открытого ключа второго устройства.

### Проверочный код

```
меньший, больший = два открытых ключа, упорядоченные побайтно (лексикографически, как memcmp)
h                = SHA-256(меньший || больший)
n                = первые 4 байта h как беззнаковое целое big-endian
код              = n mod 1 000 000, десятичными цифрами, дополнить нулями слева до 6 символов
```

Порядок аргументов не важен: оба устройства получают один код. Если сервер подменил чей-то открытый ключ,
коды на телефонах не совпадут.

### Завёрнутый ключ

```
общий_секрет   = X25519(свой закрытый ключ, открытый ключ другого устройства)   // 32 байта
ключ_обёртки   = HKDF-SHA256(IKM = общий_секрет, salt = пусто, info = utf8("one-to-one key-wrap v1"), L = 32)
nonce          = 12 случайных байт
aad            = открытый ключ отправителя (32) || открытый ключ получателя (32)
ct, tag        = AES-256-GCM(ключ_обёртки, nonce, ключ пары (32 байта), aad)
завёрнутый     = 0x01 || nonce (12) || ct (32) || tag (16)                   // всегда 61 байт
```

Формат тот же, что у конверта записи. Получатель считает тот же `ключ_обёртки` из своего закрытого ключа и открытого
ключа отправителя и открывает конверт с тем же AAD. AAD привязывает завёрнутый ключ к тем открытым ключам, по которым
партнёры сверили код, и к направлению: конверт не открыть как отправленный в обратную сторону.

### Известное ограничение: перебор ключей сервером

Код из 6 цифр — это миллион вариантов. Если сервер видит оба открытых ключа до того, как подставить свой, он может
перебрать около миллиона своих пар X25519 (секунды на обычном компьютере) и найти ту, что даёт тот же код на обоих
телефонах. Защита — обязательство (commitment), как в ZRTP: первое устройство сначала публикует только
`SHA-256(свой открытый ключ)`, второе — свой открытый ключ, и только потом первое раскрывает свой ключ; второе
проверяет, что ключ совпал с обязательством. Тогда сервер выбирает подмену, не зная ключа, и угадывает код
с вероятностью один на миллион. Поле с обязательством — `requesterKeyCommitment` в `keyRequests`, порядок шагов
описан в `docs/server.md` и сделан в `Sync/Pairing/KeyHandoff.swift`. Формулы выше при этом не меняются.

Обязательство: `SHA-256(открытый ключ X25519 запрашивающего, 32 байта)`, 32 байта, на сервере в base64.
Запрашивающий раскрывает ключ, только когда в строке уже есть ключ отвечающего, и потом берёт завёрнутый ключ,
только если ключ отвечающего в строке тот же, по которому считали код, и человек сам подтвердил код.
Отвечающий показывает код, только если SHA-256 раскрытого ключа совпал с обязательством, и заворачивает ключ пары
только после подтверждения кода.

## Открытый текст записи

Конверт защищает содержимое и место записи, но не время правки и не удаление: `$updatedAt` документа сервер ставит
сам, а конверт может стереть или заменить старым. Поэтому движок синхронизации (`RecordSealer`, `SyncEngine`) шифрует
запись целиком, и слияние верит только расшифрованному. Открытый текст конверта — JSON в UTF-8, ключи по алфавиту,
без пробелов:

```
{"id":"period:2026-10-11","payload":"e30=","updatedAt":813000000.5}
{"id":"period:2026-10-11","payload":null,"updatedAt":813000000.5}
```

- `id` — id записи (`"<вид>:<ключ>"`), из него считается `documentID`. Если `documentID` от расшифрованного `id`
  не совпал с документом, в котором лежал конверт, запись пропускается.
- `payload` — байты значения записи в base64 (стандартный алфавит, с `=`); `null` — запись удалена (надгробие).
  Удалённая запись тоже уходит конвертом.
- `updatedAt` — время правки, секунды от 1 января 2001 UTC (как `Date` в Swift), дробное число. Слияние: побеждает
  больший `updatedAt`, при равенстве — удаление, затем больший `payload` побайтно (байты без знака, как memcmp).
  Записи, сделанные до синхронизации, уходят с самым ранним временем `-63114076800` (`Date.distantPast`):
  любая версия с сервера их перебивает.
- Документ без конверта, с конвертом, который не открылся, или с неразборчивым JSON пропускается.
- Если на сервере версия старее известной телефону (откат или чужая старая правка), телефон отправляет свою снова.

## Тестовые векторы

Входы фиксированы, nonce заданы явно (в приложении они всегда случайные). Ключи X25519 взяты из RFC 7748, раздел 6.1.
Все значения совпали побайтно у CryptoKit и у независимой реализации на `node:crypto` (Node.js 26).
Строки `имя = значение` читает тест `testVectorsMatchDocs`; значения без кавычек, байты в hex.

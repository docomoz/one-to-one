# Свой сервер вместо iCloud: аккаунты, пары, синхронизация

Дизайн по итогам брейншторма 11 октября 2026. Заменяет решение «Синхронизация и аккаунты через iCloud (CloudKit)» и задачи 16–18 из `docs/plan.md` (#24, #25, #26).

## Зачем

Приложение выходит в магазины приложений для всех желающих, а не только для нас двоих. Кроме iPhone будут Android, веб, macOS и Windows, причём в одной паре у одного может быть iPhone, а у другого Android. iCloud работает только у Apple, поэтому нужен свой сервер.

Начинаем с России, потом весь мир. Данные очень личные: секс, месячные, симптомы, риск беременности. Утечка или чужой доступ к ним хуже любого бага.

## Цели запуска

Запуск iPhone-версии в App Store **через неделю** (около 18 октября 2026). **Дата важнее объёма** (решение Максима): если не успеваем, режем по списку «Что режем первым» ниже, а не переносим запуск. К запуску должны работать:

1. **Аккаунты.** Вход по почте с 6-значным кодом (без пароля) и «Войти с Apple». Удаление аккаунта прямо в приложении.
2. **Пары.** Один создаёт пару и приглашает партнёра, второй принимает. Имя и пол выбираются, как сейчас в знакомстве. Пару одного пола создать нельзя (как сейчас).
3. **Синхронизация.** Всё, что сейчас лежит в `AppData`, кроме кэшей, общее для двух телефонов пары. Без сети приложение работает как сейчас и досылает изменения, когда сеть появится.
4. **Сквозное шифрование.** Записи пары шифруются на телефоне. Сервер, а значит и мы, владельцы сервиса, прочитать их не можем.
5. **Восстановление через партнёра.** Новый телефон или своё второе устройство получает ключ от партнёра или от своего другого устройства.
6. **Юридический минимум для России и App Store:** согласие на обработку данных при входе, политика конфиденциальности, удаление аккаунта.

## Что режем первым, если не успеваем
*Порядок мой, Claude:*
1. «Войти с Apple»: хватит входа по почте с кодом. Если других способов входа нет, App Store вход с Apple не требует.
2. Перенос того, что уже записано на телефоне, в пару (см. ниже): пара просто начинается пустой.
3. Своё второе устройство: на запуске есть только iPhone, достаточно восстановления через партнёра.

Не режем: шифрование, синхронизацию без потерь, приглашение, восстановление через партнёра, согласие и удаление аккаунта.

## Не входит в запуск (потом, отдельными задачами)

- Уведомления («Пора выбрать фильм 🍿», «У вас совпадение! 💘»). Бывшая #26.
- Android, веб, macOS, Windows. Но всё, что делаем сейчас (формат данных, шифрование, протокол), должно быть реализуемо на этих платформах без переделки сервера.
- Вход через Google (появится вместе с Android).
- Пароль восстановления для тех, кто пользуется приложением один.
- Сервер для остального мира (скорее всего, второй, в Европе).

## Анти-цели (провал, даже если «работает»)

- Сервер, админка или резервные копии содержат записи пары в читаемом виде.
- Одновременные правки двух партнёров затирают друг друга, например она отметила месячные, а его запись секса пропала.
- Бывший партнёр после выхода из пары продолжает получать новые записи.
- Данные российских пользователей лежат на серверах вне России.
- Приложение без сети перестаёт работать или теряет записи.

## Ограничения

- **152-ФЗ.** Персональные данные граждан России хранятся на серверах в России. Данные о сексе и здоровье относятся к особой категории, на них нужно отдельное явное согласие. Владелец (Максим) подаёт уведомление в Роскомнадзор как оператор. До публикации тексты согласия и политики показываем юристу. Юристу же задаём вопрос, не подпадает ли приложение со сквозным шифрованием под требования к «организаторам распространения информации».
- **Хостинг: Timeweb Cloud**, аккаунт у Максима, сервер в российском дата-центре.
- **Команда:** двое без опыта программирования, каждый со своим Claude Code. Сервер должен быть таким, чтобы его можно было обслуживать по инструкции: обновления, резервные копии.
- **App Store:** удаление аккаунта в приложении; если есть вход через сторонние сервисы, нужен «Войти с Apple»; в анкете про экспорт отметить, что используется шифрование.
- **Минимальная iOS 26** (как сейчас), bundle id `com.docomoz.onetoone`.
- Существующие правила проекта: логика в `Packages/OneToOneKit` с тестами, вью отдельно, новые зависимости записываются в `docs/decisions.md`.

## Что решено

### Сервер: готовый Appwrite, а не свой код
Ставим на облачный сервер Timeweb открытую систему **Appwrite** (своя установка). В ней уже есть аккаунты (почта с кодом, «Войти с Apple» через нативный вход по токену), база с правами доступа, команды с ролями, функции на сервере, а позже рассылка уведомлений. Официальные библиотеки есть для Apple, Android, веба и Flutter. Причина: за неделю без опыта писать и защищать свой сервер с нуля нереально.
*Мой выбор, Claude:* последняя стабильная версия Appwrite на момент установки (сейчас 2.x, база PostgreSQL). Сервер не меньше 2 CPU, 4 ГБ RAM и 2 ГБ swap (минимум из документации Appwrite).

### Пара = команда Appwrite
Каждая пара соответствует одной команде (Team) в Appwrite. Права на документы пары выдаются через `Role.team(<id пары>)`, поэтому чужие пары ничего не видят. Выход из пары удаляет членство, и сервер перестаёт отдавать бывшему партнёру документы пары, включая новые. Это закрывает анти-цель про бывшего без смены ключа.

### Шифрование
- У пары есть **общий ключ** (симметричный, 256 бит). Он хранится только на устройствах партнёров, в системном хранилище ключей (на iPhone это Keychain), и на сервер не уходит никогда.
- Каждая запись шифруется на устройстве перед отправкой. Алгоритмы только стандартные и доступные на всех платформах (например, AES-GCM, X25519), чтобы Android и веб могли читать те же данные. У зашифрованного содержимого есть номер версии формата.
- **Сервер видит:** почту, имя аккаунта Apple, кто с кем в паре, id и время изменения записей, их количество и размер. **Сервер не видит:** содержимое записей и имена/пол внутри пары, если они лежат в зашифрованной части. (Где хранить имя и пол, решает исполнитель; главное, чтобы интимные данные были только в зашифрованной части.)
- **Приглашение — удалённое** (решение Максима): ссылкой или кодом в мессенджере. Ключ пары идёт через сервер только в зашифрованном виде, через обмен ключами между двумя устройствами. Чтобы сервер не мог подменить ключи, при первом соединении оба телефона показывают один и тот же короткий код (4–6 цифр), и партнёры сверяют его голосом или в переписке. Пока код не подтверждён, ключ не передаётся.
- **Восстановление** устроено так же, как приглашение, только к своему аккаунту: новое устройство получает ключ с устройства партнёра (или своего другого) через обмен ключами со сверкой кода. Удобнее всего вживую по QR-коду, но можно и удалённо с кодом. *(Мой выбор, Claude: один механизм на оба случая.)*
- **Один ключ на всю пару**, включая её симптомы и настроение. То, что у него на экране их нет, — устройство экрана, а не защита от партнёра. *(Мой выбор, Claude; Максим не ответил явно.)*

### Восстановление
- **Новый телефон:** вход в аккаунт, затем экран «Попроси партнёра открыть приложение и показать код». После передачи ключа записи открываются. До этого аккаунт есть, но записи закрыты.
- **Своё второе устройство:** так же, ключ передаётся со своего другого устройства или от партнёра.
- **Оба потеряли устройства:** записи пары пропадают. Приложение честно предупреждает об этом при создании пары.
- **Пользуются одни, без пары:** восстанавливать не через кого. Приложение предупреждает, что при потере телефона записи пропадут. Пароль восстановления добавим позже отдельной задачей.

### Синхронизация
- Без сети приложение работает как сейчас: локальный файл остаётся источником для экранов, изменения ставятся в очередь и уходят на сервер, когда сеть появится.
- **Правки не должны затирать друг друга:** данные хранятся на сервере не одним большим файлом, а отдельными записями (единица — на выбор исполнителя, например одна запись секса, один день цикла, одна оценка фильма). Если оба изменили одну и ту же запись, побеждает более поздняя правка. Разные записи сливаются без потерь.
- **Не синхронизируется:** `movieCache` и офлайн-каталог фильмов (`MovieCatalogCache.json`), это кэш каждого телефона.
- Совпадения в фильмах и риск беременности, как и сейчас, считает телефон.

### Аккаунт нужен всем
*Мой выбор, Claude:* без аккаунта приложением не пользуются. Кто пользуется один, тот в «паре», куда партнёр ещё не вошёл: имя и пол партнёра вводятся, как сейчас в знакомстве, пригласить его можно позже. Отладочное «переключиться на партнёра» на одном телефоне остаётся только в отладочной сборке, для тестов на одном телефоне.

### Выход из пары
*Мой выбор, Claude:* «Выйти из пары» входит в запуск. Записи пары стираются с телефона того, кто вышел, сервер больше не отдаёт ему документы пары. Новая пара всегда начинается с нового ключа и без записей прошлой пары (записи бывшего партнёра никуда не переносятся).

### Где доступно
*Мой выбор, Claude:* на старте приложение доступно только в российском App Store, чтобы пока не подпадать под GDPR. Другие страны откроем вместе с сервером для остального мира.

### Аккаунты и вход
- Вход по почте с 6-значным кодом и «Войти с Apple». Вход через Google появится с Android.
- Для писем с кодом нужен почтовый сервис (SMTP) с отправкой из России. Какой именно, выбирает исполнитель.
- При первом входе приложение показывает согласие на обработку данных, включая особую категорию, и ссылку на политику конфиденциальности. Без согласия дальше не пускает.
- Удаление аккаунта в приложении удаляет аккаунт и членство в паре. Если в паре остался второй партнёр, записи пары остаются у него.

### Что уже записано на телефоне
Если у того, кто **создаёт** пару, на телефоне есть записи, они загружаются в пару. У того, кто **входит по приглашению**, локальные записи заменяются записями пары; перед этим приложение предупреждает. Сейчас пользуемся только мы двое, но могут быть настоящие записи цикла.

## Что остаётся исполнителю

- Схема коллекций в Appwrite, единица синхронизации, формат зашифрованной записи (с версией).
- Протокол передачи ключа при приглашении и восстановлении: обмен ключами, коды подтверждения, срок жизни приглашения.
- Функции на сервере, если они нужны (например, принять приглашение по коду, удалить аккаунт).
- Почтовый сервис для кодов, домен, HTTPS, резервные копии и инструкция по обновлению сервера.
- Разбивка на задачи размером на один чат и их порядок. Задачи #24–#26 и раздел «Синхронизация» в `docs/plan.md` переписываются под этот дизайн, решение про iCloud в `docs/decisions.md` заменяется новым.

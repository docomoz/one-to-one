# one-to-one

iOS-приложение для пар (можно пользоваться и одному): заметки, календарь и всё нужное в одном месте. Делаем вдвоём (Дарья и Максюша), каждый со своим Claude Code. Опыта программирования у нас нет: объясняй коротко и по делу.

## С чего начинать каждый чат
1. `git pull` на `main`, сразу за ним `xcodegen generate` (без него Xcode не увидит новые файлы; если xcodegen нет, поставь `brew install xcodegen`), затем своя ветка.
2. Прочитать задачу (issue), на которую ссылается пользователь. Если номер задачи не назван, покажи открытые задачи из колонки Todo (`gh project item-list 1 --owner DariaPrishchepa --format json`) и спроси, какую берём, в таком виде:
   > Есть открытые задачи, какую берём в работу?
   > - #4 Тест: пройти цикл задачи на README — одна строка, что нужно сделать

   Задачи с незакрытыми зависимостями помечай «ждёт #N». Свою рекомендацию ставь первой.
3. По необходимости: `docs/spec.md` (что строим), `docs/plan.md` (как строим), `docs/decisions.md` (уже принятые решения). Не читай всё подряд, только нужное для задачи.

## Стек
- SwiftUI, только iOS. Минимальная версия iOS: решим в `docs/decisions.md`.
- Бэкенд с аккаунтами и синхронизацией пары: выбираем на этапе спецификации.
- Сборка и тесты:
  - Один раз: `brew install xcodegen`.
  - Логика: `cd Packages/OneToOneKit && swift test`
  - Приложение: `xcodegen generate && xcodebuild test -project OneToOne.xcodeproj -scheme OneToOne -destination 'platform=iOS Simulator,name=iPhone 17'`
  - CI тесты приложения на симуляторе не запускает, только собирает приложение и тесты (`build-for-testing`). Перед PR с изменениями экранов запускай их локально командой выше.
  - `OneToOne.xcodeproj` генерируется из `project.yml` и в git не хранится. После `git pull` выполняй `xcodegen generate`.
  - Ключи API и команда для подписи: скопируй `Config/Secrets.example.xcconfig` в `Config/Secrets.xcconfig` и впиши свои.
  - Базовый каталог фильмов для подбора без сети (`Packages/OneToOneKit/Sources/MovieAPI/Resources/movies.json`, топ-150 Кинопоиска) обновляй раз в месяц: `cd Packages/OneToOneKit && swift run UpdateMovies` (нужен ключ Кинопоиска в `Config/Secrets.xcconfig`, тратит 3 запроса).

## Как работаем
- Одна задача = один issue = одна ветка = один PR. Ветки: `feat/…`, `fix/…`, `chore/…`, `docs/…`.
- В `main` только через PR. Напрямую в `main` не пушим.
- Коммиты маленькие и осмысленные, сообщения на русском в повелительном наклонении («Добавить экран заметок»).
- Перед PR: сборка и тесты проходят, `/code-review` прогнан, найденные проблемы исправлены.
- Ревью напарника не ждём, всё обсуждаем голосом. Сразу после открытия PR ставь его на автослияние: `gh pr merge --squash --delete-branch --auto`. GitHub сам вольёт PR, когда `ci` станет зелёной; ждать и опрашивать проверки не нужно.
- Ветка PR должна быть свежей: если PR не вливается, потому что ветка отстаёт от `main` («not up to date»), выполни `gh pr update-branch`, затем `git pull` в своей ветке (иначе следующий push не пройдёт). Автослияние останется включённым и сработает после зелёной `ci`. Если есть конфликт с `main`, подтяни `main` локально (`git pull origin main`), разреши конфликт, запусти тесты, запушь.
- Влит ли PR, проверяй командой `gh pr view <N> --json state`. Если `MERGED`, переведи задачу на доске в Done.
- В описании PR: что сделано, как проверить, что осталось. Это передача контекста напарнику.
- Первая строка описания PR всегда ссылка на задачу: `Closes #N` (как в шаблоне PR). Слово обязательно английское: по русскому «Закрывает» GitHub issue не закроет. Так GitHub сам закроет issue после merge, а из PR видно, зачем он. Если делаем без issue (правка процесса), напиши «Без задачи: …» и причину.
- Новые фичи и изменения поведения: сначала скил brainstorming, потом writing-plans, потом TDD (Superpowers).
- Когда план готов (`docs/plan.md` или план фичи), разбей его на issues по шаблону `.github/ISSUE_TEMPLATE/task.md` (цель, критерии готовности, что затрагивает, от чего зависит), размером на один чат. Создай их через `gh issue create --label task`, добавь каждую на доску (команда ниже), покажи пользователю список «#N название — описание».
- Принятое решение (библиотека, архитектура, отказ от фичи) записываем одной строкой в `docs/decisions.md` с причиной.
